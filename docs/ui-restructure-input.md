# AI-Rider Video 界面重构输入文档

## 文档目的

这份文档用于给 ChatGPT 或其他设计 / 产品分析模型提供完整上下文，帮助其理解：

- AI-Rider Video 当前是什么产品
- 当前已经有哪些功能
- 哪些功能正在演进中
- PRD 里后续还会增加哪些能力
- 为什么现有配置界面开始不够用了
- 下一版界面应该遵循什么原则

这不是单纯的视觉润色需求，而是一次围绕产品结构、操作效率和后续可扩展性的界面重构输入。

## 一、产品当前定位

AI-Rider Video 原本是一个围绕“首帧 + 尾帧 + 提示词”的视频生成工具，先从本地 Web 工具发展为桌面端产品雏形。

现在产品已经进入 `2.x` 阶段，目标从单一工具升级为具备以下方向的产品：

- 多模型适配
- 多模板工作流
- 多模态输入能力
- 多 API 路径
- 激活码与商业化机制
- Web 兼容和 AI-Rider 工具体系预留

因此，现有界面不能再继续按“单模型、单玩法、单路径”的思路堆字段。

## 二、当前已经实现的功能

以下是当前代码中已经存在、用户已经可以直接使用或看到的功能。

### 2.1 基础产品结构

- 桌面端 / 本地 Web 运行能力
- AI-Rider 品牌名称与 Logo
- 中英文切换
- 浅色 / 深色主题切换
- 任务列表与任务详情
- 本地下载目录展示与打开
- 项目目录名称记录

### 2.2 模型与能力结构

- 模型注册表机制已建立
- 当前已接入 `Seedance 2.0`
- 当前已接入 `Seedance 2.0 Fast`
- 当前保留 `Seedance 1.5 Pro`
- 当前保留多个 `Seedance 1.0` 系列模型
- 模型支持能力通过注册表描述，而不是写死在页面逻辑中
- 默认模型已切换到 `Seedance 2.0`
- 模型能力会影响模板可选项

### 2.3 当前可见模板

当前产品已经开始从“单一表单”转向“模板驱动”：

- 首尾帧生成
- 首帧生成
- 文生视频
- 视频延展（实验模板）

说明：

- 模板会影响输入结构
- 模型切换后，模板列表会按支持能力过滤
- 模板与模型共同决定当前表单呈现方式

### 2.4 当前通用配置项

这些配置项属于“公共能力”，大概率后续多数模型和模板都会继续共用：

- API Key
- 模型选择
- 生成模板选择
- 生成模式：单镜头 / 多镜头
- 视频名称
- 项目目录
- 画幅比例
- 分辨率
- FPS
- 轮询间隔
- 随机种子
- 水印开关
- 生成音频开关
- 提交策略 / 模型说明
- 额外参数 JSON
- 创建任务接口
- 查询任务接口模板
- 本地费用估算单价

### 2.5 当前模板相关输入

当前模板切换后，输入区会动态变化：

- 首尾帧生成：首图 + 尾图 + 提示词
- 首帧生成：首图 + 提示词
- 文生视频：提示词
- 视频延展：参考视频 + 提示词

### 2.6 多镜头工作流

当前仅在首尾帧模板下开放多镜头模式：

- 多镜头数量配置
- 每个镜头独立首尾帧、时长、提示词
- 自动生成相邻镜头之间的 4 秒转场任务

### 2.7 任务结果与调试信息

当前任务卡已经可以展示：

- 状态
- 进度
- 视频名称
- 镜头编号
- 实际模型 / 请求模型
- 比例 / 分辨率 / 时长 / FPS
- 水印 / 音频开关状态
- 原始返回 JSON
- 视频 URL
- 本地下载视频路径
- Token 消耗
- 费用预估

### 2.8 成本相关

当前已经支持：

- 从真实任务返回中读取 `usage.total_tokens`
- 从真实任务返回中读取 `usage.completion_tokens`
- 本地配置“元 / 千 Token”单价
- 自动显示任务级费用预估

默认单价：

- `0.016 元 / 千 Token`

## 三、当前已经预留但未完全打通的能力

以下能力已经在代码结构或模型元数据中有预留，但还没有真正形成成熟用户流程。

### 3.1 多模态扩展能力

`Seedance 2.0` 在模型元数据中已经暴露：

- `MultimodalToVideo`
- `VideoExtension`
- `VideoEditing`

输入模态已知包括：

- text
- image
- video
- audio

当前问题：

- UI 只接通了部分模板
- `video_extension` 仍属于实验接入
- `video_editing` 还未进入正式界面
- `audio` 参考输入还未进入表单

### 3.2 Happy Horse 预留层

当前已经为 `Happy Horse` 做了结构性预留：

- provider 已预留
- model family 已预留
- supports / taskTypes / inputModalities 已预留

当前问题：

- 还未真实接入模型 ID
- 还未提供可选模型入口
- 还未定义专属配置项

### 3.3 更丰富的模板系统

当前模板体系还只是第一版，后续应继续扩展：

- 视频编辑
- 多模态混合生成
- 音频驱动生成
- 专属模型模板

### 3.4 更细的模型专属配置

当前额外参数仍主要靠 JSON 透传，不利于长期产品化。

后续需要考虑：

- 把高频模型专属配置提到显式 UI
- 把低频配置继续保留为高级参数

### 4.3 商业化分层

PRD 已明确产品分层方向：

- 免费工具能力
- 用户自带 API 能力

当前问题：

- 现在界面还没把这三条路径真正分开表达

### 4.4 Web 兼容

后续产品不仅服务桌面端，还要兼容 website。

当前问题：

- 现在很多界面和交互仍然偏桌面本地思维

## 六、为什么现有界面开始跟不上

当前界面的问题，不是“样式不好看”这么简单，而是信息架构已经不适配当前产品阶段。

### 6.1 当前界面起源于单工作流

原始界面是围绕：

- 首尾帧
- 单模型
- 单 API
- 单路径

设计的。

现在产品已经变成：

- 多模型
- 多模板
- 多模态
- 多路径
- 成本可见
- 后续还会有额度和商业层

### 6.2 公共配置与模板配置混在一起

当前页面上，很多“全局参数”和“当前模板专属输入”仍然堆在一个连续表单里，阅读和理解成本开始变高。

### 6.3 高级配置正在膨胀

随着模型、模板、成本、API、商用能力增加，高级配置区已经不只是“少数高级参数”，而在慢慢变成第二个配置面板。

### 6.4 任务结果区信息密度越来越高

随着 token、费用预估、模型调整说明、兼容说明等信息加入，任务详情未来也需要更清晰的层次划分，而不是纯文本堆叠。

## 七、希望界面重构优先解决的问题

以下是这次界面优化最核心的目标。

### 7.1 让用户先选“玩法”，再填“参数”

即：

- 先理解当前想做的是哪种模板
- 再看到该模板需要哪些输入
- 最后再去碰通用参数和高级参数

### 7.2 公共配置与差异配置分层

建议让用户自然理解：

- 哪些参数几乎所有模板都共用
- 哪些参数是当前模板才出现
- 哪些参数是当前模型才支持

### 7.3 模型切换后，界面能自适应

理想状态：

- 模型切换后，不支持的模板自动隐藏或禁用
- 模型支持的视频 / 音频 / 首尾帧能力会直接影响表单呈现
- 模型专属字段在合适位置显式出现

### 7.4 多镜头工作流不应挤压普通单镜头流程

多镜头是高级工作流，不应该让普通用户第一次打开就被它的复杂度干扰。

### 7.5 为后续额度 / API / 商用层预留位置

界面重构时，应考虑未来会出现：

- API 提供方切换
- 激活码状态
- 剩余次数
- 商用额度
- 成本对比

这些都不能再临时塞到现有顶部或表单末尾。

## 八、推荐的界面重构思路

以下是建议的方向，用于辅助 ChatGPT 进行更系统的设计思考。

### 8.1 视图层建议

建议界面至少分成几个明确区域：

- 顶部状态区
  - 品牌
  - 版本
  - 下载目录
  - 任务统计
  - 语言 / 主题

- 玩法入口区
  - 模板卡片
  - 模板说明
  - 当前模型支持情况

- 核心生成区
  - 当前模板专属输入
  - 当前任务主提示词
  - 当前模板摘要

- 通用参数区
  - 比例
  - 分辨率
  - FPS
  - 时长
  - 水印
  - 音频
  - 随机种子

- 提供方 / 成本 / 高级配置区
  - API 配置
  - 成本单价
  - 高级 JSON
  - 调试接口

- 任务结果区
  - 当前任务
  - 历史任务
  - 费用 / token / 模型信息
  - 原始返回

### 8.2 交互层建议

- 先选模板，再选模型，或允许模型和模板双向约束
- 模型变化后，模板列表实时变化
- 模板变化后，输入区实时变化
- 不支持的能力应明确禁用，而不是静默失效
- 实验模板要带明显标识

### 8.3 信息密度建议

- 普通用户默认只看到核心路径
- 高级用户可展开更多控制
- 多镜头、接口、成本、原始返回等不应争抢首屏注意力

## 九、对 ChatGPT 的具体任务要求

如果把这份文档提供给 ChatGPT，希望它输出的不是单纯的“更好看的页面”，而是以下内容：

1. 一个更合理的界面信息架构
2. 一个更适合未来扩展的操作流程
3. 哪些模块适合首屏展示，哪些适合折叠或分区
4. 模板系统、模型系统、多镜头系统、API 系统如何排布
5. 如何兼顾新手易用和高级用户控制力
6. 一版既美观又实用的操作界面视图建议

## 十、补充说明

- 当前产品并不只是一个“表单工具”，而是在往“多模型视频生成工作台”演进。
- 这次界面重构不应只围绕当前字段摆放，而应围绕未来 `2.x` 的产品形态来设计。
- 设计目标不是炫技，而是降低复杂度、提升理解效率、为后续增长留足结构空间。
