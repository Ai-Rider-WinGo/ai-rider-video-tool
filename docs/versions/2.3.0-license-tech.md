# AI-Rider Video 2.3.0 激活码系统技术设计

## 一、目标

本设计用于支撑 `2.3.0` 激活码系统的第一版研发与测试，覆盖：

- 本地桌面端激活状态存储
- 注册码生成与管理
- 服务端校验与扣次
- 任务创建与扣次联动
- 未来远程服务化迁移

## 二、当前实现边界

第一版先采用“单机可跑、后续可迁移”的实现方式：

- 当前服务端：本地 `server.js`
- 当前存储：本地 JSON 文件
- 当前发码工具：本地 CLI
- 当前验证：本地服务端统一处理

这版主要用于：

- 桌面端功能联调
- 激活码机制自测
- 后续迁移到真实云服务前的业务闭环验证

## 三、数据文件

建议使用以下文件：

- `settings.json`
  - 保存本机激活状态与设备信息
- `licenses.json`
  - 保存注册码主数据、设备绑定、扣次记录、事件日志

## 六、服务端接口

### 用户侧接口

- `GET /api/license/status`
- `POST /api/license/activate`
- `POST /api/license/consume`
- `POST /api/license/deactivate`

### 管理侧接口

- `GET /api/admin/licenses`
- `GET /api/admin/licenses/:code`
- `POST /api/admin/licenses/generate`
- `POST /api/admin/licenses/freeze`
- `POST /api/admin/licenses/revoke`
- `POST /api/admin/licenses/reset-devices`

## 七、任务扣次时机

任务扣次规则如下：

1. 用户已完成激活
2. 创建任务前检查激活状态与剩余次数
3. 调用视频创建接口
4. 只有在成功拿到 `taskId` 后才执行扣次

这样可避免因为参数错误、网络失败或任务创建失败而误扣次数。

## 八、未来迁移路径

当前本地 JSON 方案的结构需要和未来远程服务保持一致。

后续迁移时只需要替换：

- `license-store` 的底层读写
- 激活与扣次接口的实际运行位置

不需要重写桌面端业务流程。
