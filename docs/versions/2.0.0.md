# AI-Rider Video 2.0.0 PRD 初稿

## 文档信息

- 产品名称：`AI-Rider Video`
- 版本号：`2.0.0`
- 文档类型：产品需求文档（PRD）初稿
- 当前阶段：规划阶段
- 承接版本：`1.1.3`

## 一、背景

`1.x` 阶段，AI-Rider 已经完成从本地 Web 工具到桌面端产品雏形的推进，跑通了首尾帧视频生成的基础流程，并逐步补齐了品牌、桌面运行环境、交互体验、响应式适配和发布素材。

但从产品结构看，当前版本仍然主要围绕单一模型与单一路径设计，核心逻辑更接近“一个可用的桌面工具”，还没有真正形成适合长期演进的产品层结构。

`2.0.0` 的目标不是继续在 `1.x` 上做零散增强，而是完成一次明确的产品升级：让 AI-Rider Video 从单一工作流工具，升级为支持多模型、多 API、激活码机制和 Web 兼容的产品。

## 二、版本定位

如果说 `1.x` 解决的是：

- 把首尾帧生成视频工具做出来，并打磨成能稳定使用的桌面产品

那么 `2.0.0` 解决的是：

- 把 AI-Rider Video 从单一工具升级为支持多模型、多 API、可激活、可扩展到 Web 的产品

这一版是 AI-Rider 从“工具可用”走向“产品体系化”的第一步。

## 三、版本目标

`2.0.0` 的核心目标共有五项：

1. 扩展模型能力，从单模型工作流升级为多模型适配结构。
2. 升级 API 架构，支持用户自带 API 与 AI-Rider 商用 API 并存。
3. 建立基础商业闭环，引入激活码与次数机制。
4. 让桌面端与未来 Web 端共用一套产品逻辑。
5. 为 AI-Rider 后续更多工具预留可复用的产品层结构。

## 四、2.x 版本拆分原则

为了避免后续把 `2.0.0` 当成一个无限膨胀的大版本，`2.x` 建议按“主线阶段 + 子版本号”的方式推进。

建议规则如下：

- `2.0.x`：架构重组与基础能力接入阶段
- `2.1.x`：产品化表达与可用性增强阶段
- `2.2.x`：Web 兼容与服务化准备阶段
- `2.3.x`：商业化增强与体系联动阶段

对应理解：

- `x.0.0` 表示一个新阶段的起点版本
- `x.0.1`、`x.0.2` 表示该阶段内的补强和收口
- 不建议把所有能力都堆到单个 `2.0.0`

阶段目标：

- `AI-Rider Video` 开始具备接入 AI-Rider 主体系的能力

## 六、核心问题定义

### 6.1 模型耦合过强

当前版本的默认参数、任务提交流程和交互细节，仍然较强地依赖现有模型能力，导致后续接入新模型时容易牵动整套界面和服务逻辑。

`2.0.0` 需要把模型能力从界面逻辑中抽离出来，形成统一的模型适配层，让不同模型以统一方式接入产品。

### 6.2 API 路径单一

当前主路径仍然偏向用户自己配置 API 并自行运行任务，缺少同时支持“自带 API”和“平台提供 API”的产品层设计。

`2.0.0` 需要支持两条路径长期并存：

- 用户自带 API
- AI-Rider 提供的商用 API

### 6.3 缺少可运营机制

`1.x` 更像一个可用工具，尚未建立完整的可分发、可控制、可收费机制。

`2.0.0` 需要补齐以下能力：

- 激活码
- 次数限制
- 免费与收费分层
- 商用 API 调用管理

### 6.4 产品形态过度依赖桌面端实现

当前实现以桌面端、本地文件和本地配置为中心，未来如果直接迁移到 Web，会面临较多逻辑耦合和平台差异问题。

`2.0.0` 需要开始拆分“产品逻辑”和“平台实现”，为 `ai-rider.xyz` 的后续部署打基础。

## 七、目标用户

本版本主要面向三类用户：

### 7.1 创作者型用户

- 需要快速生成首尾帧视频
- 不希望自己研究复杂接口和参数
- 更适合直接使用 AI-Rider 提供的商用 API

### 7.2 进阶工具型用户

- 有自己的 API Key 和模型偏好
- 希望自行控制成本和调用路径
- 更适合使用自定义 API 模式

### 7.3 AI-Rider 早期体验用户

- 希望先试用产品
- 对工具有兴趣，但尚未进入付费阶段
- 适合通过激活码获取一定次数体验

## 八、产品范围

### 8.1 本版本包含

- 多模型适配层设计与基础落地
- 多 API 提供方结构设计
- 激活码与剩余次数基础机制
- 免费与商用能力的产品表达
- 桌面端与 Web 兼容边界梳理
- `Seedance 2.0` 的能力预研与接入准备

### 8.2 本版本暂不包含

- 完整支付系统
- 完整账号体系
- 多工具统一后台
- 大规模运营后台
- 所有目标模型的一次性全部接入

说明：`2.0.0` 优先解决产品结构问题，不追求在一个版本内完成所有商业化与平台化能力。

## 九、核心使用场景

### 9.1 首次体验场景

- 用户第一次打开产品
- 用户对模型和 API 细节不了解
- 用户希望先体验一次完整生成流程

本场景下，产品需要优先提供：

- 清晰的模式说明
- 激活码入口
- 默认可用的推荐模型
- 最小可操作参数集合

### 9.2 自带 API 创作场景

- 用户已有自己的 API Key
- 用户希望自己控制模型、成本和调用来源
- 用户更关注灵活性而不是平台兜底

本场景下，产品需要优先提供：

- 自定义 API 配置入口
- 提供方与模型的清晰映射
- 稳定的参数与任务提交流程

### 9.3 平台直连使用场景

- 用户不想处理复杂接口配置
- 用户希望即开即用
- 用户对价格、额度和剩余次数更敏感

本场景下，产品需要优先提供：

- AI-Rider 商用 API 模式
- 剩余次数或额度展示
- 足够清晰的消耗提示

### 9.4 多平台延展场景

- 同一套产品逻辑未来需要同时服务桌面端与 Web 端
- 用户在不同平台上应获得尽量一致的理解方式

本场景下，产品需要优先保证：

- 产品结构一致
- 核心流程一致
- 平台差异仅出现在文件与系统能力层

## 十、核心功能模块

### 10.1 模型适配层

这是 `2.0.0` 的核心基础模块。

目标：

- 把不同模型能力抽象成统一结构
- 避免后续每接入一个模型就重写一套界面或提交逻辑
- 为未来继续扩展模型预留稳定入口

建议抽象字段：

- 模型 ID
- 模型显示名称
- 提供方
- 支持的任务类型
- 是否支持首尾帧
- 是否支持文本生成视频
- 是否支持音频
- 时长限制
- 分辨率限制
- 参数映射规则
- 默认值
- 能力说明

本阶段重点方向：

- `Seedance 2.0` 预研
- `Happy Horse` 预留
- 其他模型接入预留

### 10.2 API 提供方层

目标：

- 不让产品绑定单一 API 来源
- 不同来源共用统一任务工作流
- 降低用户理解成本

建议支持的模式：

#### 模式 A：用户自定义 API

- 用户填写 API Key
- 用户填写接口地址
- 用户自行承担生成成本
- 更适合进阶用户和开发者用户

#### 模式 B：AI-Rider 商用 API

- 用户直接使用 AI-Rider 提供的生成能力
- 用户不需要处理复杂接口配置
- 更适合普通使用者和体验型用户

界面建议：

- 增加 API 模式切换
- 增加提供方配置卡片
- 为不同模式提供清晰说明和使用提示

### 10.3 激活码与次数系统

这是 `2.0.0` 的基础运营模块。

当前产品原则：

- 工具免费使用
- 激活码免费发放
- 每个激活码默认 `100 次`
- 使用完后可以后续续发

基础能力需求：

- 激活码输入
- 激活状态校验
- 剩余次数展示
- 每次生成扣减次数
- 使用完后的提示逻辑
- 后续续发机制预留

后续可扩展方向：

- 激活码批量生成
- 激活码后台管理
- 设备绑定或用户绑定
- 不同额度类型

### 10.4 商用 API 产品逻辑

本阶段不要求一次性完成复杂支付闭环，但要先把产品分层表达清楚。

建议产品分层：

- 免费工具能力
- 用户自带 API 能力
- AI-Rider 商用 API 能力

建议用户理解路径：

- 想自己折腾：填写自己的 API
- 想直接使用：选择 AI-Rider 商用 API
- 想先体验：通过激活码获得一定次数

本模块重点不在“立即支付”，而在于先把产品逻辑表达清晰，为后续商业化留出标准入口。

### 10.5 Web 兼容层

`2.0.0` 需要开始以未来部署到 `ai-rider.xyz` 为前提做结构设计。

建议共用内容：

- 产品结构
- 模型适配层
- API 提供方层
- 激活码逻辑
- 页面文案和信息结构

桌面端特有内容：

- 本地文件选择
- 本地目录写入
- 本地任务文件组织
- 原生窗口能力

Web 端需替代内容：

- 文件上传改为浏览器上传
- 文件下载改为浏览器下载
- 本地目录逻辑改为项目空间或云端任务空间

这一模块的关键目标是：将当前代码从“桌面实现导向”逐步转向“产品逻辑 + 平台适配”的结构。

### 10.6 AI-Rider 体系兼容性

`AI-Rider Video` 是 AI-Rider 工具体系的第一款产品，但不应被设计为孤立工具。

`2.0.0` 需要预留以下兼容方向：

- 产品命名体系化
- API 层后续支持多工具复用
- 激活码体系后续支持多工具共用
- 官网结构后续支持多工具承载
- 用户体系后续支持跨工具统一

## 十一、关键页面与信息结构

建议 `2.0.0` 至少围绕以下页面或视图组织信息：

### 11.1 工作台首页

- 模型选择
- API 模式选择
- 首尾帧上传入口
- 提示词输入
- 核心参数区
- 提交按钮

首页原则：

- 先满足最短路径可用
- 高级参数不抢占核心操作区
- 模型与 API 的当前状态要可见

### 11.2 API 与账号能力区

- 自定义 API 配置
- AI-Rider API 模式说明
- 当前激活状态
- 剩余次数或额度

页面原则：

- 配置逻辑集中
- 免费与商用边界说明清晰
- 避免把复杂配置散落在多个页面

### 11.3 任务结果区

- 当前任务状态
- 历史任务记录
- 结果预览
- 下载与导出入口

页面原则：

- 任务创建、处理中、完成、失败要有明确状态
- 结果信息与消耗信息尽量同屏可见

### 11.4 产品说明区

- 当前版本说明
- 支持的模型与模式说明
- 激活码和体验规则说明

页面原则：

- 解释放在合适位置，不干扰主流程
- 让新用户能快速理解产品分层

## 十二、用户路径

### 12.1 路径一：体验型用户

1. 打开产品
2. 输入激活码
3. 查看剩余次数
4. 选择模型与基础参数
5. 提交生成任务
6. 扣减次数并返回结果

### 12.2 路径二：自带 API 用户

1. 打开产品
2. 进入 API 配置
3. 选择自定义 API 模式
4. 填写 Key、接口地址和模型参数

### 12.3 路径三：商用 API 用户

1. 打开产品
2. 选择 AI-Rider 商用 API 模式
3. 查看当前可用额度或体验次数
4. 选择模型并提交任务
5. 返回生成结果和使用消耗提示

- 商用 API 收费
- 激活码用于体验和分发
- 用户自带 API 模式长期保留

- 先跑通激活码与次数逻辑

### 13.3 后续可演进方向

- 套餐制
- 次数包
- 月度订阅
- 多工具通用额度

## 十六、依赖与风险

### 16.1 外部依赖

- `Seedance 2.0` 的能力边界与接口稳定性
- 后续候选模型的可接入性
- AI-Rider 商用 API 的服务可用性
- Web 部署阶段的服务层准备情况

### 16.2 主要风险

- 如果模型能力差异过大，统一参数层可能被迫过度抽象
- 如果 API 提供方差异过大，可能导致“统一工作流”表面统一、底层复杂度过高
- 如果过早引入支付、账号、后台，容易把 `2.0.0` 范围拉得过大
- 如果桌面端历史实现拆分不干净，后续 Web 化成本会显著上升

### 16.3 风险应对原则

- 先抽最小通用层，不追求一次性覆盖所有未来模型
- 先定义产品层规则，再接入具体提供方
- 先跑通最小商业闭环，再讨论复杂支付和账户体系

## 十七、待确认事项

以下内容建议在 `2.0.0` 开发前继续明确：

1. `Seedance 2.0` 首批支持哪些任务能力。
2. `Happy Horse` 在 `2.0.0` 中是仅预留，还是要实际接入。
3. 激活码的校验是在本地完成、服务端完成，还是采用混合方式。
4. AI-Rider 商用 API 在 `2.0.0` 中是否已经需要区分不同额度类型。
5. Web 端首期是完整产品同步，还是先提供简化版体验入口。

## 十八、版本边界

`2.0.0` 不是最终商业版本，也不是完整 Web 版本。

这一版的交付重点是：

- 定义清晰的产品结构
- 建立可继续扩展的模型与 API 架构
- 建立最基础的激活码机制
- 为后续 Web 化和 AI-Rider 工具体系打地基

换句话说，`2.0.0` 的价值在于“把方向和结构立住”，而不在于一次性把所有功能铺满。

## 十九、成功标准

如果 `2.0.0` 达到以下状态，即可认为本版本目标基本成立：

1. 产品已不再依赖单一模型结构。
2. 用户可以在自带 API 与 AI-Rider API 之间切换。
3. 激活码与次数逻辑已建立最小闭环。
4. 桌面端实现不再把核心逻辑写死在平台层。
5. 后续迁移到 Web 时，无需重做产品层结构。

## 二十、一句话总结

`AI-Rider Video 2.0.0` 是一次从“可用工具”走向“产品体系化”的升级：它将为多模型、多 API、激活码机制和 Web 部署建立统一结构，并成为 AI-Rider 工具体系的第一块正式地基。
