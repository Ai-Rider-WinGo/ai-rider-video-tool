# AI-Rider Video 2.3.0 激活码与注册码系统方案

## 文档信息

- 产品名称：`AI-Rider Video`
- 版本阶段：`2.3.0`
- 文档类型：产品方案 + 技术方案初稿
- 目标平台：`macOS` / `Windows`
- 当前状态：方案确认中

## 一、方案定位

`2.3.0` 的激活码系统，不只是一个“输入注册码才能继续”的弹窗功能，而是 AI-Rider Video 商业化与分发体系的基础设施。

这一版要解决的是：

- 软件安装后如何建立最小使用门槛
- 免费体验码、测试码、正式注册码如何统一管理
- 使用次数如何被准确扣减
- mac / Windows 客户端如何安全存储激活状态
- 你如何自己生成、发放、冻结和查询注册码

一句话定义：

**AI-Rider Video 2.3.0 = 桌面端必须激活，服务端校验，服务端扣次，用户通过微信领取或购买注册码，你通过内部工具统一生成和管理注册码。**

## 二、核心产品目标

本方案的核心目标有五个：

1. 软件安装后必须完成激活才能正式使用
2. 激活码按次数分档，支持 `5 / 50 / 100 / 1000` 次
3. 每次正式创建生成任务时扣减次数
4. 用户通过微信联系你领取或获取激活码
5. 由你掌控发码工具，所有注册码只能由你的后台工具生成

## 三、产品规则

### 3.1 激活规则

- 用户首次安装并启动软件后，默认进入激活引导页
- 未激活用户不能正式发起视频生成
- 激活成功后才能进入主工作台
- 客户端必须联网完成首次激活

### 3.2 次数档位

建议首版支持四档：

- `5 次`
- `50 次`
- `100 次`
- `1000 次`

建议补充两个内部用途类型：

- `测试码`
- `赠送码`

### 3.3 扣次规则

首版建议采用最简单也最清晰的规则：

- 本地参数校验失败：不扣次
- 图片/视频上传失败：不扣次
- 服务端创建任务失败：不扣次
- 服务端成功创建任务并返回任务 ID：扣 `1` 次

不按视频时长、模型价格、镜头数量做复杂扣减。首版先保持“一次创建任务 = 一次扣减”。

### 3.4 设备绑定规则

首版建议：

- 一个注册码默认绑定 `1 台设备`
- 测试码或内部码可配置 `2~3 台设备`
- 管理端支持手动重置设备绑定

这样可以降低滥用，又不会过度增加正常用户的使用摩擦。

## 四、安装后的用户路径

你提到“安装完成后提醒添加微信，给激活码”，这个我建议正式做成产品路径，而不是零散文案。

### 4.1 首次安装路径

1. 用户安装并打开软件
2. 显示欢迎与激活引导页
3. 页面展示：
   - 产品简介
   - 当前版本
   - 微信二维码
   - `添加微信获取激活码`
   - `我已有激活码`
4. 用户扫码添加微信
5. 你手动发放激活码
6. 用户回到软件输入激活码
7. 软件联网校验并激活
8. 激活成功后进入主工作台

### 4.2 首次页建议文案

建议主文案：

- `欢迎使用 AI-Rider Video`
- `首次使用需要激活码`
- `添加微信领取体验码或正式注册码`

建议按钮：

- `添加微信获取激活码`
- `输入激活码`

建议辅助文案：

- `激活后即可开始使用视频生成工作台`
- `注册码按剩余次数控制可用额度`

### 4.3 为什么先走微信

这一条非常适合你当前阶段：

- 你可以手动筛选用户
- 你可以观察真实需求
- 你可以先不接支付系统
- 你可以通过微信完成售前沟通、体验码发放和后续续发

所以首版路径不需要急着做“官网购买 -> 自动发码”，先走微信反而更稳。

## 五、激活码状态设计

每个激活码至少应有以下状态：

- `unused`：未激活
- `active`：已激活，可继续使用
- `exhausted`：次数耗尽
- `revoked`：已作废
- `expired`：已过期
- `frozen`：已冻结

建议补充说明：

- `unused` 和 `active` 都可能允许继续激活，但受设备绑定规则约束
- `exhausted` 不允许继续生成
- `revoked` 和 `frozen` 由后台人工控制

## 六、客户端行为设计

### 6.1 mac / Windows 客户端策略

客户端不要保存“真实剩余次数”，真实状态必须以服务端为准。

客户端本地只保存：

- 激活成功后的授权 token
- 最近一次同步的只读激活状态缓存
- 设备指纹信息

### 6.2 本地安全存储建议

- `macOS`：使用 `Keychain`
- `Windows`：使用 `Credential Manager` 或系统安全存储

不要把完整激活码明文长期写入普通配置文件。

### 6.3 离线策略

首版不建议支持完全离线激活。

建议规则：

- 首次激活必须联网
- 使用过程中可以短时离线展示最近缓存状态
- 正式扣次前必须联网验证

## 七、服务端方案

### 7.1 为什么不能只做本地注册码

如果只在本地校验注册码：

- 很容易被反编译或跳过校验
- 剩余次数可以被本地篡改
- 激活码可以被复制给多人使用

所以首版必须采用：

**服务端生成 + 服务端验证 + 服务端扣次**

### 7.2 服务端职责

服务端需要负责：

- 注册码生成
- 激活码状态管理
- 设备绑定
- 剩余次数扣减
- 使用记录留痕
- 异常冻结与人工处理

## 八、后台生成工具方案

你明确提出“需要一个生成注册码的软件，所有注册码都需要我来通过软件生成”，这个建议完全成立。

首版建议做一个你自己使用的内部后台工具。

### 8.1 管理工具核心能力

- 选择注册码档位：`5 / 50 / 100 / 1000`
- 生成单个注册码
- 批量生成注册码
- 查看注册码状态
- 查询某个注册码的剩余次数
- 冻结/作废注册码
- 重置设备绑定
- 导出 CSV
- 添加备注

### 8.2 建议的注册码格式

建议使用人眼可读且便于复制的格式：

`AIRV-50A2-9XQK-7MPL`

建议规则：

- 固定品牌前缀：`AIRV`
- 中间为随机编码段
- 不直接暴露次数信息
- 后台内部单独存档位和额度

也可以附加校验位，但首版不是必须。

### 8.3 管理工具形态建议

首版最实用的两个选择：

1. `Web 管理后台`
2. `桌面内部工具`

我更推荐首版用 `Web 管理后台`：

- 部署简单
- 数据集中
- 后续更容易加账号和权限
- 生成工具不依赖某一台电脑

## 十二、安全建议

首版建议做到这几个最有价值的点：

1. 注册码只在服务端生成
2. 客户端不保存真实剩余次数
3. 每次创建任务前服务端扣次
4. 加入设备绑定
5. 所有激活和扣次写操作都记录日志

首版可以先不做：

- 完整防逆向体系
- 离线授权文件
- 多层代理分销码
- 加密 USB dongle 之类重方案

## 十三、测试建议

研发时建议覆盖这些测试场景：

### 13.1 激活测试

- 正常激活
- 激活码不存在
- 激活码已冻结
- 激活码已用尽
- 激活码超设备上限

### 13.2 扣次测试

- 创建任务成功，扣 1 次
- 创建任务失败，不扣次
- 网络异常，不扣次
- 边界值：剩余 `1` 次时再创建任务

### 13.3 设备测试

- 同设备重复激活
- 新设备激活
- 设备重置后重新绑定

### 13.4 后台测试

- 单个生成注册码
- 批量生成注册码
- 冻结/作废
- 查询与导出

## 十五、结论

这套方案适合 AI-Rider Video 当前阶段，因为它同时满足三件事：

- 你能控：注册码由你自己生成和发放
- 用户能用：安装后路径简单直接
- 后续能长：可以平滑接到支付、官网和统一账户体系

当前建议正式定版为：

**AI-Rider Video 桌面端首次安装后显示微信引导与激活页，用户通过微信获取注册码，注册码按次数分档，服务端完成校验与扣次，你通过后台工具统一生成和管理所有注册码。**
